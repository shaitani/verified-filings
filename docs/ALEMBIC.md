# Alembic — database migrations

Alembic turns the SQLAlchemy models into PostgreSQL tables and keeps the
database in step as they change. Run every `alembic` command **from the
repository root**.

## Where things are

| path | what |
|---|---|
| `alembic.ini` | Alembic's config. Points at the migrations folder; the database URL is **not** here |
| `app/db/migrations/env.py` | wires Alembic to this project: the URL from `app.config.settings`, both model metadatas (`xbrl` and `web`), and autogenerate limited to those two schemas |
| `app/db/migrations/versions/` | one file per migration |
| `app/db/models.py`, `app/db/web.py` | the models migrations are compared against |
| `.env` | `DATABASE_URL` (the real database) and `DATABASE_URL_TEST` (tests only) |

Facts worth knowing:

- Every table lives in a named PostgreSQL schema: `xbrl` (the filings) or
  `web` (users, conversations, jobs). Alembic's own `alembic_version` table,
  one row naming the applied migration, lives in `public`.
- Migrations run as the `postgres` superuser, which is why they can `CREATE
  SCHEMA` and `CREATE TYPE`.
- The login roles are **not** migrations (see
  [BOOTSTRAP.md](BOOTSTRAP.md#what-is-deliberately-not-automated)). A migration
  that adds a table needs a re-run of `uv run python -m app.db.roles`.
  `vf_query_mapper_role` picks up new `xbrl` tables through default
  privileges; `vf_retrieval_role` and `vf_web_role` deliberately do not — add
  the table to their `RoleSpec` in `app/db/roles.py` if they should reach it.
  Re-running is also how a changed grant is applied: provisioning revokes
  before it grants.

**The database URL**, from `docker-compose.dev.yml`:

```
postgresql+asyncpg://postgres:postgres@localhost:5432/verified_filings
└───────┬────────┘   └──┬───┘ └──┬───┘ └───┬───┘ └┬─┘ └──────┬───────┘
   dialect+driver      user    password    host  port     database
```

`app/config.py` reads whichever `DATABASE_URL` is in the environment — a real
environment variable wins over `.env`. That is how one command points Alembic
at the test database without editing a file (below). It has to be the literal
URL: `DATABASE_URL_TEST` exists only inside `.env`, which the shell never sees.

## When you need a migration

Any change to `app/db/models.py` or `app/db/web.py` that changes **database
structure**: a table, a column (added, removed, renamed, retyped, nullability,
default), an index or constraint, or a value added to an enum.

Not for: comments or docstrings, `relationship()` changes that do not change a
foreign key, or anything outside the model files.

## Writing one

1. Database running: `docker compose -f docker-compose.dev.yml up -d`.
2. Generate the file (writes a file, touches no database):

   ```
   uv run alembic revision --autogenerate -m "short description"
   ```

3. **Read the new file and fix it by hand.** Autogenerate is not reliable for
   this schema:

   | thing | what to do |
   |---|---|
   | expression indexes (`uq_fact_natural` uses `coalesce(...)`) | may show a spurious drop-and-recreate; delete those lines if the index did not change |
   | new enum types | make `downgrade()` remove them: `op.execute("DROP TYPE IF EXISTS xbrl.<name>")` |
   | new enum values | not generated. Add by hand: `op.execute("ALTER TYPE xbrl.<name> ADD VALUE '<value>'")` — cannot run inside a transaction |
   | a new PostgreSQL schema | `CREATE SCHEMA` is never generated; the first migration using one adds it by hand, as for `xbrl` and `web` |
   | a CHECK generated by a type (`sa.Enum(..., native_enum=False)`) | `alembic check` compares CHECKs by name and does not see a type's own, so it proposes dropping the database's. Declare the CHECK explicitly, named, on a plain `String` column (`app/db/web.py` `_one_of`) |
   | a table a role may write but not read (`web.job_trace`, `web.job_feedback`) | a model setting, not a migration one: `__mapper_args__ = {"eager_defaults": False}`, or the ORM's `INSERT ... RETURNING` needs `SELECT` and is refused |
   | library column types (`fastapi_users_db_sqlalchemy.generics.GUID`) | written unimported; replace with the plain type they compile to (`sa.UUID()`, `sa.DateTime(timezone=True)`) |

   Check both `upgrade()` and `downgrade()`.

4. Apply it — to **both** databases (commands: [STARTUP.md](STARTUP.md#4-database-schema--both-databases)).
5. Confirm the real database matches the models:

   ```
   uv run alembic check
   ```

   Expected: `No new upgrade operations detected.`

6. If a role should reach a new table, re-run `uv run python -m app.db.roles`.
7. Commit the migration with the model change, together.

## Handy commands

| command | purpose |
|---|---|
| `uv run alembic current` | which migration is applied |
| `uv run alembic history` | every migration, oldest first |
| `uv run alembic upgrade head --sql` | print a migration's SQL without running it |
| `uv run alembic downgrade -1` | undo the most recent migration |
| `uv run alembic downgrade base` | undo everything — empties `xbrl` and **drops `web` with every user and conversation** |

## Rules

- One migration per logical change.
- **Never edit a migration that has already been applied to a shared
  database.** Write a new one.
